## What just happened

`count++` looks like one step, but the CPU does three: read `count`, add 1, write it back. T2 read `count` before T1 had written its new value, so both threads started from 0 and both wrote 1. One update was lost.

## Why it's hard to catch

The bad interleaving needs both threads to land in the same tiny window. On a quiet laptop that rarely happens, so tests pass. Under real load, with more threads and more cores, it happens all the time.

## Try the what-if switch

Both fixes make read-add-write behave as one step, in different ways:

- **synchronized**: only one thread can be inside `increment()`. T2 sat `BLOCKED` until T1 released the lock (the *monitor*), then read the fresh value.
- **AtomicInteger**: no lock. `compareAndSet` writes only if the value is still what you read. T2's CAS failed because T1 got there first, so T2 read again and retried. Nobody waited.

| | synchronized | Atomic (CAS) |
| --- | --- | --- |
| Under contention | threads wait | threads retry |
| Protects | any block of code | one variable |
| Good for | several fields that change together | counters, flags, single values |

## Rule of thumb

If two threads touch the same variable and at least one of them writes, you need synchronization. For a counter, `incrementAndGet()` does the CAS loop for you. Once two values must change together, like a balance and a log, use a lock: two separate atomics can't keep them consistent.
